  <name>Task 1 : Un seul helper de conversion, dans les deux sens</name>
  <files>app/src/lib/datetime.ts, app/src/lib/datetime.test.ts</files>
  <behavior>
    - `instantToLocalInput('2026-10-15T16:30:00+00:00')` rend l'heure **locale** du navigateur correspondante (`2026-10-15T18:30` à Paris), jamais la chaîne UTC tronquée.
    - `localInputToInstant('2026-10-15T18:30')` rend `2026-10-15T16:30:00.000Z` à Paris.
    - Aller-retour : `localInputToInstant(instantToLocalInput(iso))` redonne le **même instant** pour dix formes d'entrée (avec `Z`, avec offset, avec millisecondes).
    - Deux allers-retours consécutifs ne déplacent plus la valeur (le défaut de WR-07 : dérive de 2 h par enregistrement).
    - Valeur vide, `null`, `undefined`, chaîne invalide → `''` en relecture et `null` en écriture, jamais `NaN`, jamais `Invalid Date`.
    - Année bissextile : `localInputToInstant('2028-02-29T09:00')` est un instant fini.
  </behavior>
  <action>
Créer `app/src/lib/datetime.ts` — le point unique de D-05, sur le modèle des helpers de
`lib/utils.ts` (pas de classe, pas d'état) :

1. `datetimeLocalOf(instant: string | null | undefined): string` — un **instant** (ISO avec
   `Z` ou offset, ou `Date`) rendu en `YYYY-MM-DDTHH:mm` du fuseau **local** du navigateur :
   c'est la forme qu'attend `<input type="datetime-local">`. Utiliser `format` de `date-fns`
   (`"yyyy-MM-dd'T'HH:mm"`), jamais `slice`. Chaîne invalide ou vide → `''`.
2. `instantOfDatetimeLocal(value: string): string | null` — la valeur d'un
   `datetime-local` (`YYYY-MM-DDTHH:mm`, **interprétée en local** par `new Date`) rendue en
   ISO UTC (`toISOString()`). Vide ou invalide → `null` (chaîne vide = « aucun rappel »,
   convention déjà portée par `taches/types.ts:72`).
3. Nommer les deux directions dans le **même** module, avec un commentaire qui dit pourquoi :
   `slice(0, 16)` sur un instant UTC est le défaut d'origine — le commentaire cite WR-07 et
   D-05 pour que la prochaine relecture ne le réintroduise pas.

Écrire `app/src/lib/datetime.test.ts` en suivant `app/src/lib/utils.test.ts` (Vitest, pas de
rendu). Le test doit être **indépendant du fuseau de la machine** : calculer l'attendu avec
`date-fns`/`Intl` dans le test plutôt que de coder « 18:30 » en dur — sauf pour l'assertion
d'aller-retour, qui est vraie dans tous les fuseaux.

Prouver rouge→vert : réintroduire temporairement un `slice(0, 16)` dans la relecture, constater
l'échec de l'assertion d'aller-retour, restaurer, constater le vert.
  </action>
  <verify>
    <automated>cd app && npm test -- src/lib/datetime.test.ts && npm run typecheck</automated>
  </verify>
  <done>
    Les deux directions vivent dans `lib/datetime.ts`, l'aller-retour est prouvé sur des formes
    d'entrée variées, et aucune valeur invalide ne produit `NaN`.
  </done>
</task>
