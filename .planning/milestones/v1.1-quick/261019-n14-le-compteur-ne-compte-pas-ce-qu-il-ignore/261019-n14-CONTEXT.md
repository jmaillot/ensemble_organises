# CONTEXT — 261019-n14

## Ce qui a été mesuré (pas déduit)

**Le flake documenté ne se reproduit plus.** 16 tentatives avec le code d'aujourd'hui :
4 suites complètes (1292 tests chacune, ~8 min pièce) et 12 passages ciblés des deux
fichiers **sous 4 brûleurs CPU**. Zéro échec. Le TODO, lui, avait mesuré **2 échecs sur 4**
le 2026-10-18.

**La politique réseau n'est pas l'explication.** Source installée lue :
`@tanstack/query-core/build/modern/onlineManager.cjs` — `#online = true` **en dur**,
`navigator` **jamais lu**, seuls les événements `online`/`offline` de `window` le font
changer (`if (this.#online !== online)`). Aucune requête de ces tests ne peut donc se mettre
en pause, ni avant ni après `261019-dw6`. Attribuer la disparition du flake à `dw6` serait
une affirmation non vérifiée (§2.7 I) — elle n'est pas écrite.

**La cause réelle du flake est le défaut que cette tâche corrige.** Les deux fichiers
concernés mesurent tous les deux un compteur **dérivé d'une lecture encore en vol**, et le
code répond « toutes les tâches du foyer » au lieu de « je ne sais pas » :

- `app/src/app/app-shell.tsx:80-92` : `taskAssigneesQuery.data ?? []` → tant que la lecture
  des assignations n'a pas rendu, `assigneeByTask` est vide, donc chaque tâche tombe dans
  `assignees.length === 0` → **toutes** les tâches ouvertes sont comptées. Le badge affiche
  le total du foyer.
- `app/src/hooks/use-notifications.ts:138-146` + `:280-286` : même lecture, même règle, dans
  le centre de notifications → les tâches **des autres** y figurent.

Ce qui le rend visible en test : les deux assertions ne **s'arrêtent pas sur un état**, elles
attendent un budget.

- `app/src/hooks/use-notifications.test.tsx:19-24` porte déjà
  `configure({ asyncUtilTimeout: 8000 })`, avec ce commentaire : « Fichier temps réel … sur
  machine chargée (suite complète), le délai d'1s des `waitFor` est trop court et fait
  flaker. 8s absorbe les pics sans masquer un vrai blocage. » Le délai a été **relevé** à
  l'endroit où le défaut se manifestait.
- `app/src/app/app-shell.test.tsx:261-267` n'a aucun relèvement : `await
  within(nav).findByLabelText('1 tâches ouvertes')` avec le budget par défaut (1 s). Sous
  charge, la lecture des assignations arrive après l'expiration → rouge.

Conséquence importante pour la fiabilité des deux gardes : **le correctif seul ne suffit
pas**. En attendant d'être « connue », la valeur devient absente ; un `findBy*` continuerait
donc d'expirer sous charge. Les gardes doivent attendre un **état** (la lecture des
assignations a abouti), pas une durée.

## Décisions verrouillées

1. **Une seule couture**, `app/src/hooks/use-open-task-assignees.ts`, lue par le shell ET le
   centre de notifications : la requête (même clé, même `queryFn`) **et** la règle
   « une tâche sans assigné (foyer) ou assignée à moi ».
2. **L'ambiguïté est dans le TYPE, pas dans un commentaire.** La couture rend une union
   discriminée `{ state: 'unknown' } | { state: 'known'; byTask }`. Un appelant ne peut pas
   oublier de traiter « on ne sait pas » : il n'a pas de tableau vide à lire.
3. **Ce qu'affiche un état inconnu : rien.** Le badge « tâches ouvertes » ne se rend pas ; la
   cloche n'ajoute aucune ligne `tache`. Rien n'est affirmé sur ce qu'on ignore — c'est la
   leçon de `dw6` appliquée à un compteur, pas une nouvelle règle de goût.
4. **La portée de chaque compteur ne change pas.** Le shell compte les tâches `a_faire` hors
   voyage ; la cloche compte les tâches non `fait` hors voyage. Cette différence est
   antérieure et n'est pas rouverte : seule l'ambiguïté de la lecture est corrigée.
5. **Les deux tests gardent leur sens.** Ils continuent d'exiger « 1 » et l'exclusion des
   tâches de Thomas : c'est le défaut qu'ils visent. Seule la **façon d'attendre** change —
   un état, jamais un budget. Le relèvement à 8 s n'est **pas** retiré : d'autres assertions
   du même fichier (ligne 504 : budget au-dessus de l'`asyncUtilTimeout`) s'appuient sur lui,
   et une ligne que cette tâche ne peut pas prouver nécessaire resterait une ligne non
   vérifiée.
6. **Second défaut, même famille : `local-adapter.seedNow()` marque une table « amorcée »
   avant de l'écrire.** Mise en évidence par une sonde déterministe (écrite, exécutée,
   supprimée) : dès qu'une passe d'amorçage échoue, les tables parcourues restent marquées,
   la passe de rattrapage les **saute**, et la base reste vide (`tasks=0`,
   `task_assignees=0`) — définitivement, pour ce fichier de test ou cette session de démo.
   Correction : marquer **après** l'écriture réussie.
7. **Ce que cette tâche n'affirme pas** : que le défaut 6 explique le flake du 2026-10-18.
   Un échec de passe vide un **préfixe** de la liste des tables (`tasks` compris), or le
   constat ne voyait qu'un test en échec par fichier. Ça ne colle pas, donc ce n'est pas
   écrit.
